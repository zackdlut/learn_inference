Tokenizer 图解：GPT-2 的 byte-level BPE

对应本项目 tokenizer.hpp / tokenizer.cpp， 词表文件由 tools/convert_gpt2.py 从 data/gpt2/vocab.json、merges.txt 转换而来。 页面里所有例子都是用与 tokenizer.cpp 相同的算法、在真实的 GPT-2 词表上跑出来的（"The capital of France is" 的结果与 convert_gpt2.py 中的参考 token 一致）。 图中 ␣ 表示空格，↵ 表示换行。

1. 总览：encode 的四步，decode 的三步

原理

模型只认识整数，分词器负责文本和整数之间的双向翻译。把 encode 写成函数复合：

\[ \mathrm{encode}(s) = \mathop{\Vert}_{c\,\in\,\mathrm{pre}(s)} \mathrm{lookup}\Big(\mathrm{bpe}\big(\mathrm{map}(\mathrm{bytes}(c))\big)\Big) \]

其中 \(\mathrm{pre}\) 是预分词，\(\mathrm{map}\) 是字节到可见字符的映射，\(\mathrm{bpe}\) 在每个词块内部做合并，\(\mathrm{lookup}\) 查词表，\(\Vert\) 表示把各词块的结果按顺序拼接。decode 是逆过程，并且对任意 id 序列都成立：

\[ \mathrm{decode}(\mathrm{encode}(s)) = s \]

这个"无损往返"是 byte-level 设计带来的：最底层是 256 个字节，任何 UTF-8 文本都能被表示，也都能被还原。

3. 第一步 pre_tokenize：先切成"词块"

优先级GPT-2 官方正则的分支pre_tokenize 里的对应逻辑例子
1's|'t|'re|'ve|'m|'ll|'d遇到 ' 时比较 7 个后缀I'm → I'm
2 ?\p{L}+可选 1 个前导空格 + 连续 is_letter␣learning
3 ?\p{N}+可选 1 个前导空格 + 连续 is_digit␣314
4 ?[^\s\p{L}\p{N}]+可选 1 个前导空格 + 连续"非空白、非字母、非数字"!␣=.
5\s+(?!\S)|\s+连续空白；若后面还有非空白，把最后一个空格让给下一块↵↵␣␣y

每个例子切出来的词块

原理

为什么要先切块：BPE 只在词块内部合并，合并永远不会跨越词块边界。这样 "dog." 和 "dog!" 里的 "dog" 会得到同一个 token，而不会学出 "dog." 这种把标点粘进单词的 token，词表的利用率更高。

为什么空格放在单词前面：规则 2~4 都允许"一个可选的前导空格"，所以 GPT-2 的 token 大多是 "Ġthe"、"Ġcapital" 这种"空格 + 单词"的形式。句首的 "The" 没有前导空格，是另一个 token（464），而 " The" 是 383。

规则 5 的细节："x = 3.14↵↵␣␣y" 中的空白串 ↵↵␣␣ 后面跟着 y，正则 \s+(?!\S) 要求匹配结束后不能紧跟非空白，于是只吃掉 ↵↵␣，把最后一个空格留给 ␣y。tokenizer.cpp 里的 --end 就是在实现这个"让出一个空格"。

4. 第二步 byte_encoder：256 个字节 → 256 个可见字符

行是高 4 位，列是低 4 位。蓝色 188 个字节保持原码位（!~~、0xA1~0xAC、0xAE~0xFF）； 红色 68 个控制字符、空白和不可见字节，按顺序映射到 U+0100 起的码位（256…323）。 橙框 是"你"的 3 个字节和空格、换行。

原理

映射后的字符再编码成 UTF-8 存进词表，所以需要每个字节都对应一个"能安全打印、能放进 JSON 的字符"。设保留集合为 \(K\)（\(|K| = 188\)），被移走的字节按从小到大的顺序编号为 \(j = 0, 1, \dots, 67\)：

\[ \mathrm{map}(b) = \begin{cases} \mathrm{chr}(b), & b \in K \\ \mathrm{chr}(256 + j(b)), & b \notin K \end{cases} \qquad \text{码位范围 } [\,0x21,\ 0x143\,] \]

最大码位 \(256 + 67 = 323 = \text{0x143}\)，UTF-8 下最多 2 字节，这正是 make_byte_encoder 只处理 1 字节和 2 字节两种情况的原因。映射是双射，byte_decoder 就是它的逆表。

顺带一提，词表的前 256 个 id 正好就是这 256 个字符：id 0~187 是保留字节（按字节值排序），188~255 是被移走的字节，所以空格 \(\to\) Ġ \(\to\) id \(188 + 32 = 220\)。

5. 第三步 bpe：按优先级一步步合并

原理与公式

每一轮在当前所有相邻对中，找 rank 最小（merges.txt 中最靠前）的那一对，把它在词块中所有的出现位置一起合并：

\[ (a^*, b^*) = \arg\min_{(a,b)\,\in\,\mathrm{pairs}(w)} \mathrm{rank}(a, b), \qquad w \leftarrow w\big[\,a^*\, b^* \to a^*b^*\,\big] \]

没有任何相邻对出现在 merges 里时停止。注意 encode 时看的是 rank（训练时被加入的先后），而不是在当前这个词里出现的次数。训练时规则是这样产生的：从 256 个字节出发，每次把语料中最常相邻出现的一对合并成新符号，重复 50000 次：

\[ (a,b)^{(k)} = \arg\max_{(a,b)}\ \mathrm{count}^{(k)}(a,b),\qquad \mathrm{rank}\big((a,b)^{(k)}\big) = k \]

encode 按 rank 从小到大重放这些合并，就能把新文本切成和训练时一致的 token。

复杂度：tokenizer.cpp 每轮扫描所有相邻对（\(O(n)\) 次哈希查找），最多 \(n-1\) 轮，所以单个词块是 \(O(n^2)\)。词块通常只有几个到十几个字符，这样写最直观；tiktoken 等库用优先队列加链表把它降到 \(O(n\log n)\)。

6. 第四步查词表：id 是怎么排的

原理

用 data/gpt2 里的两个文件逐条核对，50000 条合并规则全部满足

\[ \mathrm{id}(a^{(k)} b^{(k)}) = 256 + k \]

也就是说 GPT-2 的词表就是"256 个字节 + 按合并顺序依次追加的新符号 + 1 个特殊 token"，id 越小的 token 在训练语料里越早、越频繁地出现，因此 \(V = 256 + 50000 + 1 = 50257\)。这也说明 merge_rank_ 里存的行号可以直接由 id 推出：\(\mathrm{rank} = \mathrm{id} - 256\)。

byte-level BPE 里 token_to_id_ 查找失败是不可能的：BPE 的每个结果要么是单字节字符（一定在前 256 个 id 里），要么是某条规则的合并结果（一定在词表里）。所以 encode 在查不到时直接抛异常，提示词表文件不匹配。

7. decode：id → 字节 → 文字（token 边界 ≠ 字符边界）

以 "你好，世界" 为例：11 个 token、15 个字节、5 个汉字和标点。第一行是 token（id 和映射后的字符串），第二行是 decode_one 还原出的原始字节，第三行是按 UTF-8 拼出来的字符。

原理

decode_one(id) 把 token 字符串逐字符查 byte_decoder 还原成字节，decode 再把所有字节按顺序拼起来：

\[ \mathrm{decode}(\mathrm{id}_1, \dots, \mathrm{id}_n) = \mathrm{bytes}(\mathrm{id}_1) \,\Vert\, \cdots \,\Vert\, \mathrm{bytes}(\mathrm{id}_n) \]

上图里 id 19526 只有 E4 BD 两个字节，"你"的第 3 个字节 A0 在下一个 token 254 里。所以单独打印 decode_one(19526) 会得到不完整的 UTF-8，终端上显示成乱码。逐 token 流式输出时，要先把字节放进缓冲区，凑满一个完整的 UTF-8 字符（首字节 0xE? 表示共 3 字节，0xF? 表示 4 字节）再输出。

GPT-2 训练语料以英文为主，汉字的字节对很少被合并，所以中文平均每个字要 2 个左右的 token，而英文一个常见单词通常就是 1 个 token。

8. 实现细节与注意事项

① 预分词的近似：切分不同，最终 id 基本相同

官方正则用 Unicode 属性 \p{L}，tokenizer.cpp 把所有 ≥ 0x80 的字节都当作字母。对中文全角标点，两者切分不同：

但把两种切分分别交给同一个 BPE，比较上面所有例子以及约 2.3 万个"英文/中文单词 + 常见 Unicode 符号"的组合，最终 id 序列完全一致。 原因是合并规则是在官方切分出的词块内部学出来的：官方规则下"字母"和"全角标点"永远不在同一个词块里，所以它们之间的相邻对没有对应的合并规则，即使 C++ 把它们放进同一块，BPE 也不会把它们合并。 这个近似不保证在所有输入上都和官方一致（例如非 ASCII 的空白字符），但对常见文本足够。

② 合并"所有"出现位置

第 5 节的 hahaha：rank 737 的规则 a + h 在词里出现了 2 次，一轮里要同时合并。如果每轮只合并第一处，下一轮会先命中别的规则，结果就和官方对不上，tokenizer.cpp 的注释里也专门强调了这一点。

③ 为什么 merge_rank_ 的键要加 '\x01'

直接拼接会产生歧义："a" + "bc" 和 "ab" + "c" 拼出来都是 "abc"。中间插一个分隔符就能区分。选 \x01 是安全的： 映射后的字符要么是 0x21~0x7E 的单字节，要么是首字节为 0xC2~0xC5 的 2 字节 UTF-8，任何 token 字符串里都不可能出现字节 0x01。

④ 特殊 token 不会被 encode 识别
