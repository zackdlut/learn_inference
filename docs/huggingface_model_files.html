1. 目录里有什么？谁连谁？

原理与公式

从数学上看，一个"模型"可以拆成三部分：分词函数 \(\mathrm{tok}\)、由 config 决定结构的函数 \(f_{\text{config}}\)、以及从 safetensors 读出的参数集合 \(\theta\)：

\[ z = f_{\text{config}}\big(\mathrm{tok}(\text{text});\ \theta\big),\qquad \theta = \{\texttt{wte.weight},\ \texttt{h.0.ln\_1.weight},\ \dots\},\quad |\theta| = 160 \] \[ p_\theta(x_{t+1}=v \mid x_{\le t}) = \mathrm{softmax}(z_t)_v \]

同一个 \(f\)（GPT-2 架构代码）配上不同的 config 与 \(\theta\)，就得到 gpt2 / gpt2-medium / gpt2-large / gpt2-xl 等不同模型。反过来，\(\theta\) 必须配合训练时用的那个分词器：同一个 id 在不同词表里代表不同的词，换了分词器，嵌入矩阵的每一行就对不上了。

2. config.json — 架构蓝图（不含权重）

{
  "model_type": "gpt2",
  "architectures": ["GPT2LMHeadModel"],
  "n_layer": 12,
  "n_head": 12,
  "n_embd": 768,
  "n_ctx": 1024,
  "vocab_size": 50257,
  "activation_function": "gelu_new",
  "eos_token_id": 50256
}
字段在本示例中
n_layer12 个解码器块 → safetensors 里 h.0…h.11
n_embd隐藏维 768；与多数 weight 的最后一维一致
n_head12 头 × 64 维/头；c_attn 输出 2304 = 3×768
vocab_size与 wte.weight 行数 50257 一致
model_typeAutoConfig.from_pretrained 选 GPT-2 配置类
原理与公式

config 里的几个整数决定了所有张量的形状和总参数量。派生量：

\[ d_h = \frac{n_{embd}}{n_{head}} = 64,\qquad d_{ff} = 4\,n_{embd} = 3072,\qquad \dim(\text{qkv}) = 3\,n_{embd} = 2304 \]

参数量公式（记 \(d = n_{embd},\ L = n_{layer}\)）：

\[ P = \underbrace{(V + n_{pos})\,d}_{\text{wte + wpe}} + L\,\underbrace{(12d^2 + 13d)}_{\text{per block}} + \underbrace{2d}_{\text{ln\_f}} = 124{,}439{,}808 \]

fp32 存储为 \(4P \approx 498\ \text{MB}\)。实际 model.safetensors 的数据区是 548,090,880 字节，多出的 50,331,648 字节恰好是 12 个 attn.bias 因果掩码缓冲：\(12\times1024\times1024\times4\)。它们不是可训练参数，只是旧版本把掩码也一起存了进来。

把 gpt2-xl 的 config（\(L=48,\ d=1600\)）代入同一个公式，得到约 1.56B 参数。这就是为什么只换 config 就能描述整个模型家族。

3. 分词器：vocab.json + merges.txt

vocab.json：JSON 字典，键为 BPE 子词（如 Ġworld 表示前导空格+world）。 merges.txt：第 1 行 #version: 0.2；之后每行两列符号，定义合并顺序。 id 50256 = <|endoftext|>，与 config 中 eos_token_id 一致。
原理与公式

训练 BPE（生成 merges.txt 的过程）：从 256 个字节符号开始，统计语料中所有相邻符号对的出现次数，把最频繁的一对合并成新符号并记录下来，重复 50000 次：

\[ (a,b)^{(k)} = \arg\max_{(a,b)} \mathrm{count}(a,b),\qquad \mathrm{rank}\big((a,b)^{(k)}\big) = k,\quad k = 1,\dots,50000 \]

merges.txt 的第 \(k\) 行就是第 \(k\) 次合并，所以文件顺序就是优先级。编码时按 rank 从小到大贪心地应用合并（详见 推理流程页 ①）。词表大小因此是：

\[ V = \underbrace{256}_{\text{bytes}} + \underbrace{50000}_{\text{merges}} + \underbrace{1}_{\texttt{<|endoftext|>}} = 50257 \]

Ġ 的来历：GPT-2 把 256 个字节一一映射到可打印的 Unicode 字符，避免控制字符和空白出现在词表里。空格字节 0x20 被映射成 U+0120，即 "Ġ"，所以 Ġworld 就是 " world"。这样任意字节串都能写成合法的 JSON 字符串存进 vocab.json。

英文平均约 1 个 token 对应 4 个字符；中文常常 1 个汉字要 1~3 个 token，因为 GPT-2 训练语料以英文为主，汉字的字节对很少被合并。

4. model.safetensors — 二进制布局

__metadata__.format = "pt"；共 160 个张量；无独立 lm_head.weight（与 wte 共享）。
原理与公式

设文件开头 8 字节（小端 u64）解出的头部长度为 \(N\)，某张量的 data_offsets 为 \([b, e)\)，则：

\[ \text{abs\_begin} = 8 + N + b,\qquad \text{nbytes} = e - b = \Big(\prod_{i} \text{shape}_i\Big)\times \mathrm{sizeof}(\text{dtype}) \]

本文件前 8 字节是 cb 37 00 00 00 00 00 00，即 \(N = \texttt{0x37cb} = 14283\)。校验：\(8 + 14283 + 548{,}090{,}880 = 548{,}105{,}171\)，正好等于文件大小。张量内部按行优先（C 顺序）排列，二维张量元素 \((i,j)\) 的字节位置为：

\[ \mathrm{addr}(i,j) = \text{abs\_begin} + (i\cdot n_{cols} + j)\times 4 \]

例如 wte.weight 形状为 \([50257, 768]\)，token 464 的嵌入向量就是从 \(\mathrm{addr}(464, 0)\) 开始的连续 \(768\times4 = 3072\) 字节。因此加载器可以直接 mmap 整个文件，按需取片段，不必先全部读进内存。

安全性：头部是纯 JSON，解析只读数据；而 pytorch_model.bin 是 pickle 格式，反序列化时可以执行任意代码。

5. 权重在模型结构中的位置

张量名前缀数量（约）说明
wte / wpe各 1词嵌入 + 位置嵌入
h.{0..11}.*13×12每块：2×LayerNorm、Attention、MLP（含 bias/mask）
ln_f2最终 LayerNorm 的 weight / bias
原理与公式

GPT-2 的线性层用 Conv1D 实现（名字是历史遗留，实际就是全连接层），权重形状为 (in, out)：

\[ y = xW + b,\qquad W \in \mathbb{R}^{d_{in}\times d_{out}} \]

而 PyTorch nn.Linear 是 \(y = xW^\top + b,\ W\in\mathbb{R}^{d_{out}\times d_{in}}\)。所以 c_attn.weight 是 \([768, 2304]\)，而 LLaMA 等模型的 q_proj.weight 是 \([out, in]\)。把 GPT-2 权重转成 nn.Linear 风格时需要转置。各张量在前向公式中的位置（\(W_{mp}\) 即 mlp.c_proj）：

\[ \begin{aligned} X^{(0)} &= W_{te}[\mathbf{x}] + W_{pe}[0{:}T] \\ U &= X^{(\ell-1)} + \mathrm{Attn}\big(\mathrm{LN}_{\gamma_1,\beta_1}(X^{(\ell-1)});\ W_{attn}, b_{attn}, W_{proj}, b_{proj}\big) \\ X^{(\ell)} &= U + \mathrm{GELU}\big(\mathrm{LN}_{\gamma_2,\beta_2}(U)\,W_{fc} + b_{fc}\big)\,W_{mp} + b_{mp} \\ z &= \mathrm{LN}_{f}\big(X^{(12)}\big)\,W_{te}^{\top} \end{aligned} \]

最后一行就是 weight tying：输出投影直接用 \(W_{te}^\top\)，所以文件里没有 lm_head.weight，加载时要让 lm_head 指向 wte 的同一块内存。逐步的张量形状见 推理流程页。

6. 从 Hub 下载时还可能看到什么？

文件本目录常见完整仓库
tokenizer.json—Fast tokenizer 序列化（与 vocab/merges 等价信息，格式不同）
generation_config.json—默认 max_new_tokens、采样温度等（不改变权重）
pytorch_model.bin—旧版 PyTorch pickle 权重（逐渐被 safetensors 替代）
model-xxxxx-of-yyyyy.safetensors + *.index.json—大模型分片；逻辑名 → 物理文件映射

下载示例：huggingface-cli download gpt2 --local-dir data/gpt2

原理与公式

分片索引：大模型的 model.safetensors.index.json 里有一个 weight_map，本质上是一个从张量名到文件名的映射，各分片的张量名互不重叠、合起来覆盖全部参数：

\[ \mathrm{shard}: \text{tensor name} \mapsto \text{file name},\qquad \bigsqcup_{k} \mathrm{keys}(\text{shard}_k) = \text{all tensor names} \]

每个分片本身仍是一个独立、合法的 safetensors 文件，加载器先读 index，再按需打开对应分片。

generation_config.json 里的参数只作用于"logits 到下一个 token"这一步。例如温度 \(\tau\) 与重复惩罚 \(r \gt 1\)（第二个式子只作用于已经出现过的 token）：

\[ p_v \propto \exp(z_v/\tau),\qquad z_v \leftarrow \begin{cases} z_v / r, & z_v \gt 0 \\ z_v \cdot r, & z_v \le 0 \end{cases} \]

它们完全不涉及权重，只改变采样方式。

7. 与本项目 INFR 格式对照

本仓库自研 INFR（.inference） 同样采用「元数据 + 原始字节」思路，但张量命名与用途针对 MNIST 演示。 Hub 的 safetensors 则是跨框架通用权重交换格式，适合对照学习如何按名称加载 h.0.attn.c_attn.weight 这类参数。

原理与公式

两种格式的寻址公式结构相同，只是"数据区起点"的记录方式不同：safetensors 由头部长度推出，INFR 直接存一个 data_start 字段。

\[ \text{safetensors:}\ \ \text{abs} = 8 + N + b \qquad\qquad \text{INFR:}\ \ \text{abs} = \text{data\_start} + \text{offset} \]

两者都满足 \(\text{nbytes} = \prod_i \text{shape}_i \times 4\)（fp32）。因此给 ModelFile 增加 safetensors 支持只需三步：读 8 字节得到 \(N\)；解析 JSON 得到每个张量的 dtype、shape、offsets；令数据区起点为 \(8+N\)。其余的切片与拷贝逻辑可以直接复用。
