## 0. 一页看懂

问题：`C[M,N] = A[M,K] × B[K,N]`，全部 float32、行优先连续存储。

| 版本 | 函数 | 核心想法 | 解决了什么瓶颈 |
|------|------|----------|----------------|
| v1 | `matmul_f32_ijk` | 照抄数学定义 | —（基准线） |
| v2 | `matmul_f32_ikj` | 交换 j、k 两层循环 | 内层访存从「跳着读」变成「连续读」，编译器能自动向量化 |
| v3 | `matmul_f32_tiled` | 循环分块 + **B 块打包** | 让一块 B 留在 L1 被反复使用 |
| v4 | `matmul_f32_avx2` | AVX2/FMA 4×16 寄存器微内核 + **A/B 打包**（GotoBLAS） | C 的累加不再来回读写内存；读 A/B 都是连续的 |
| v5 | `matmul_f32_parallel` | 按行切给多个线程 | 用上所有核 |

本机（Intel Core Ultra 5 135U，2 P 核 + 8 E 核 + 2 LP-E 核，14 线程，15 W 笔记本）实测，
Release，GFLOPS（越大越好）：

| 版本 | 优化前 N=1024 | 最终 N=1024 | 最终 N=1000 |
|------|---------------|-------------|-------------|
| v1 朴素 i-j-k | 0.5 | 0.5 | 2.3 |
| v2 换循环顺序 | 17.0 | 18.3 | 14.8 |
| v3 循环分块 | 14.4（比 v2 还慢） | 22.2 | 20.2 |
| v4 AVX2+FMA | 32.0 | 72 ~ 78 | 63 ~ 82 |
| v5 多线程 | 55.3 | 215 ~ 253 | 222 ~ 272 |

> ⚠️ 这台机器的测量噪声非常大（同一配置前后能差 30%，持续满载降频时能差 3 倍），
> 只有**同一进程内交替运行**的对比才可信，见 [第 7 节](#7-性能测量方法论)。

## 1. 先算清楚上限

优化之前先知道「天花板」在哪，否则不知道还有多少空间、什么时候该停。

```
   一条 AVX2 指令处理 8 个 float
   FMA：一条指令同时做乘和加           → 16 FLOP / 指令
   每周期能发射 2 条 FMA               → 32 FLOP / 周期 / 核
   P 核 ~4.4 GHz（睿频，估计值）        → 单核峰值 ≈ 140 GFLOPS
```

`hello_perf` 里按「3 GHz × 7 核 ≈ 672 GFLOPS」粗估全核峰值。真实情况更复杂：
E 核的 FMA 吞吐和频率都低于 P 核，满载时整机还会降频。

**计算量**：每个 C 元素要做 K 次乘加，共 `2·M·N·K` FLOP。1024³ ≈ 21.5 亿次浮点运算。

**访存量**：A、B、C 一共 `3·N²` 个 float（1024 时 12 MB）。
计算量是 O(N³)、数据量是 O(N²) —— 每个数据理论上能被复用 N 次。
**矩阵乘法优化的全部内容，就是想办法把这个复用真正兑现出来**：
让一个数从内存搬进来以后，尽量在寄存器 / L1 / L2 里被多用几次再扔掉。

```
   存储层级（本机，大致数量级）
   ┌───────────────┬──────────┬──────────────┐
   │ 寄存器 YMM×16  │ 512 B    │ 0 周期        │
   │ L1d           │ 48 KB/核  │ ~5 周期       │
   │ L2            │ 2 MB/核   │ ~15 周期      │
   │ L3            │ 12 MB 共享 │ ~50 周期      │
   │ 内存           │ GB        │ ~200+ 周期    │
   └───────────────┴──────────┴──────────────┘
```

## 2. v1：朴素 i-j-k

```cpp
for i: for j: { sum = 0; for k: sum += a[i*K+k] * b[k*N+j]; c[i*N+j] = sum; }
```

和数学定义一一对应，是所有优化版本的**正确性参照**。

**慢在哪**：最内层是 k，`b[k*N + j]` 每次跳 N 个 float（N=1024 时 4 KB）。
每次从内存搬一整条 64 字节的 cache line，只用其中 1 个 float 就扔掉。
而且这是一个「归约」循环（`sum +=`），不开 `-ffast-math` 时编译器不敢重排浮点加法，
无法向量化。

---

## 3. v2：交换循环顺序 i-k-j

```cpp
for i: for k: { aik = a[i*K+k]; for j: c[i*N+j] += aik * b[k*N+j]; }
```

数学上完全等价，只是把 j、k 两层换了位置。最内层变成 j 之后：

- `b[k*N + j]`、`c[i*N + j]` 都是**相邻地址连续访问**，一条 cache line 的 16 个 float 全用上；
- 不同 j 之间没有依赖，编译器在 `-O3 -march=native` 下自动向量化成 AVX2 指令。

**结果**：17 ~ 18 GFLOPS，比 v1 快 30 倍以上（Debug 构建下只快 1.1 倍 ——
因为 `-O0` 不做向量化，这也说明「快」主要来自 SIMD，而 SIMD 的前提是连续访存）。

**新的瓶颈**：每做一次 8 宽的 FMA，都要从 L1 读一次 B、**读一次 C、写一次 C**。
C 在 L1 里来回读写，load/store 端口先被占满，算力用不满。
另外对固定的 i，k 要扫过整个 B（4 MB），L2 装不下，每一行 A 都要把 B 从 L3 重新流一遍。

## 4. v3：循环分块 + 打包

### 4.1 想法

把 B 切成小块，一块 B 搬进 L1 之后，让 A 的很多行都来用它，而不是每行 A 都重新从 L3 流一遍 B。

### 4.2 第一版为什么比 v2 还慢

最初的写法是直接在原矩阵上切 64×64 的块（`kTileM = kTileN = kTileK = 64`），
设想「一块 16 KB，A/B/C 三块 48 KB 刚好塞满 L1」。实测反而比 v2 慢（14.4 vs 17.0）。

用独立基准排查（换尺寸、换块大小），定位到三个原因：

**(1) 主因：4 KB 别名（cache 组冲突）**

```
   L1d 48 KB，12 路组相联，64 组 × 12 路 × 64 B
   组号 = 地址的第 6~11 位

   N=1024 时 B 相邻两行相隔 1024×4 = 4096 B = 2^12
   → 地址第 6~11 位完全相同 → 块里所有行都落进同一组（同一批 4 个组）
   → 64 行抢 12 路，块根本留不在 L1，不停互相踢出（conflict miss）
```

证据：同样的代码，N=1000 时 v3 比 v2 快 20%，N=1024 时反而慢；v2 几乎不受 N 影响
（它本来就不指望 B 留在 L1）。

**(2) 分块不解决 C 的读写瓶颈**：v2 和 v3 最内层都是「读 B、读 C、写 C」，
都被 L1 load/store 卡在 20 ~ 29 GFLOPS，分块的收益天花板本来就低。

**(3) 次因：j 循环太短**：64 个 float 只有 8 个 AVX 向量，循环开销占比大。

### 4.3 修正：打包（packing）

```cpp
// 按 (j0, k0) 切出 B 的一块，先拷贝到连续缓冲区
for (k = 0; k < kn; ++k)
    std::copy_n(b + (k0 + k) * N + j0, jn, packed + k * jn);
// 再让 A 的所有行轮流和它相乘
```

拷贝之后块内各行首尾相接，行距不再是 N，**彻底不受原矩阵尺寸是不是 2 的幂影响**。
同时把块改成 32×256（32 KB，留在 L1），j 循环变长。

块尺寸是扫参数扫出来的：

| 打包后块尺寸 | N=1000 | N=1024 |
|--------------|--------|--------|
| 未打包 64×64（原版） | 26.7 | 20.5 |
| 打包 TK32 × TN256 = 32 KB | **34.9** | **31.3** |
| 打包 TK64 × TN128 = 32 KB | 34.8 | 31.5 |
| 打包 TK64 × TN256 = 64 KB | 30.3 | 25.6 |
| 打包 TK128 × TN512 = 256 KB | 24.7 | 26.6 |

结论：**块的大小要按 L1 定（32 KB 刚好）**，大了留不住，小了循环开销大。

> 打包后每个 C 元素的累加顺序和 ikj 完全一致，所以 v3 和 v2 的结果**逐位相同**。

## 5. v4：AVX2 + FMA 寄存器微内核 + GotoBLAS 打包

### 5.1 微内核：让 C 待在寄存器里

v2/v3 的根本瓶颈是 C 在 L1 里来回读写。v4 的想法是：**一次算 C 的一个 4×16 小块，
全程放在寄存器里，K 循环结束才写回一次**。

```
            B 竖条（16 列 = 2 个 __m256）
               b0          b1
            ┌────────┬────────┐  ← 每个 k 读 16 个 B
     a0 ──→ │  c00   │  c01   │
     a1 ──→ │  c10   │  c11   │  8 个累加器，全程在 YMM 寄存器里
     a2 ──→ │  c20   │  c21   │
     a3 ──→ │  c30   │  c31   │
            └────────┴────────┘
   每个 k：2 次 B 加载 + 4 次 A 广播 + 8 条 FMA
```

为什么是 4×16：

- 16 列 = 2 个 `__m256`；4 行 × 2 = 8 个累加器；
- 再加 2 个 B 向量、1 个 A 广播 = 11 个寄存器，YMM 一共 16 个，留有余量；
- 再大就会「寄存器溢出」（spill）到栈上，反而变慢。

关键指令：

```cpp
__m256 av = _mm256_broadcast_ss(ak + r);   // 把 A 的一个标量复制到 8 个通道
c00 = _mm256_fmadd_ps(av, b0, c00);         // c00 += av * b0，一条指令、一次舍入
```

### 5.2 只有微内核还不够：B 也要打包

最初的 v4 只有微内核，直接在原矩阵上读 B：`b + k * N`。
同样撞上 4 KB 别名，而且 N=2048 时更惨（行距 8 KB，几乎每次都 miss）：

| | N=1000 | N=1024 | N=2048 |
|---|---|---|---|
| v4 未打包 | 46 | 21 | **6.5** |
| v4 打包 B | 116 | 41 | 60 |

（同一进程内交替运行的结果；多线程 v5 的提升更大：N=2048 从 11 → 191。）

打包 B 的布局：把 B 的一块切成若干条 16 列宽的**竖条**，每条按 k 连续存放，
最后一条不足 16 列补 0：

```
   原 B 块（行距 N）                打包后（第 s 列起的竖条）
   k=0: [b00 b01 ... b0,15 | ...]   packed[s*kc + 0*16 .. +15]  ← 64 B 连续
   k=1: [b10 b11 ... b1,15 | ...]   packed[s*kc + 1*16 .. +15]
   ...                               ...
```

微内核每个 k 读的正是相邻的 64 字节，硬件预取完美工作。

### 5.3 完整的 GotoBLAS 五层循环

再把 A 也打包（4 行一组，组内按 k 交错：每个 k 的 4 个数挨在一起），并给 M 方向分块：

```cpp
for jc in N step kNC:            // 切 B 的列        ┐ 打包 B 块（kKC×kNC）
  for p0 in K step kKC:          // 切 K             ┘ 被 A 的所有行复用
    pack_b(...)
    for ic in M step kMC:        // 切 A 的行         打包 A 块（kMC×kKC）
      pack_a(...)                //                  被这块 B 的所有竖条复用
      for jr in nc step 16:      // B 的一条竖条（L1）
        for ir in mc step 4:     // A 的一条横条
          micro_kernel_4x16(...)
```

每一级放什么、放在哪级 cache：

| 数据 | 尺寸 | 位置 | 被谁复用 |
|------|------|------|----------|
| C 的 4×16 小块 | 8 个 YMM | 寄存器 | 整个 kc 循环 |
| B 的一条竖条 | kKC×16 = 256×16 = 16 KB | L1 | kMC/4 条 A 横条 |
| A 的一块 | kMC×kKC = 64×256 = 64 KB | L2 | kNC/16 条 B 竖条 |
| B 的一块 | kKC×kNC = 256×512 = 512 KB | L2/L3 | A 的所有行块 |

当前参数：`kKC = 256, kMC = 64, kNC = 512`。

实现细节：

- **K 被切成多段**：第一段 `accumulate=false` 直接覆盖 C，之后的段累加，省掉预先清零；
  K=0 时分段循环一次都不执行，要单独把 C 清零。
- **边角**（不足 4 行或 16 列）：打包时已经补 0，微内核照常算，
  结果先写进 4×16 临时区，再只把有效的 mr×nr 拷回 C（`edge_tile`），避免越界写。

### 5.4 打包 A 的收益：几乎为零（但值得知道为什么）

同一进程内交替对比「只打包 B」和「A+B 都打包」：

| | 单线程 N=1000 / 1024 / 2048 | 多线程 N=1000 / 1024 / 2048 |
|---|---|---|
| 只打包 B | 117.7 / 86.4 / 61.7 | 336.0 / 274.2 / 239.3 |
| A+B 打包（MC64 NC512） | 118.5 / 83.4 / 61.5 | 321.7 / 277.3 / 266.3 |

差距在噪声范围内。原因：

- 只打包 B 时，微内核读的 A 也只是 4 行 × kc=256，共 4 KB，一直留在 L1 里，本来就不是瓶颈；
- 单线程已经到 ~118 GFLOPS，按 P 核 ~140 GFLOPS 的估算峰值，已经是 ~85%，
  剩下的空间不在 cache 层面。

保留 A 打包的理由：结构完整（标准 GotoBLAS），边角处理更简单（不用再给 A 单独补零），
以后换更大的微内核（6×16）或 K 更大时会用得上。

## 6. v5：多线程

### 6.1 按行切分

```cpp
parallel_rows(M, M * N * K, [&](int64 lo, int64 hi) {
    matmul_f32_avx2(a.subspan(lo * K, rows * K), b, c.subspan(lo * N, rows * N), rows, N, K);
});
```

- **切行不切列**：C 行优先存储，不同线程写不同的行，落在不同的 cache line 上，
  没有 false sharing（两个核抢同一条 cache line 的所有权）。
- **小问题不开线程**：`M*N*K < 2^20` 时串行。创建线程要几十微秒，算得比这还快就是赔本。
- `std::jthread`（C++20）析构时自动 join，不会忘记 join 导致 `std::terminate`。

### 6.2 踩过的坑：subspan 不带长度

最初写的是 `c.subspan(lo * N)` —— 只给起点不给长度，子 span 一直延伸到 C 的末尾。
AVX2 构建下没问题（微内核只写自己的行），但**关掉 AVX2 时 v4 回退到 v3**，
而 v3 开头会 `fill(c, 0)`，把后面其他线程负责的行一起清零 → 数据竞争、结果错误。

测试为什么没抓到：本机构建开着 AVX2，那条回退路径从来没执行过。
用 `-DINFERENCE_NATIVE_API=OFF` 单独构建才复现（多线程用例稳定失败）。

修复：

1. `subspan` 带上长度 `rows * N`；
2. `ikj`、`tiled` 的清零改成只清 `c.first(M * N)`，不信任调用方传进来的 span 长度；
3. 新增测试 `matmul_does_not_write_past_mn`：输出缓冲区比 M×N 多 64 个哨兵值，
   所有实现跑完哨兵必须原样保留 —— 串行路径就能抓到，不依赖线程调度。

### 6.3 失败的尝试：所有线程共用一份打包好的 B

v5 的每个线程都调用 v4，各自打包一整份 B，看起来重复干了 nt 倍的活。
于是试了「线程只创建一次、共用一份 B、每轮 (jc, p0) 用 `std::barrier` 对齐两次、
从原子计数器动态领工作单元」的方案（ThreadSanitizer 验证无数据竞争）。

结果多数形状**反而更慢**（GFLOPS，同一进程交替运行）：

| 形状 M×N×K | 各线程各打包一份 B | 共享 B（该形状下最好的参数） |
|---|---|---|
| 1000³ | 262 | 226 |
| 2048³ | 99 | **137** |
| 16×3072×768 | 33 | 34 |
| 64×3072×768 | 68 | **99** |
| 128×768×3072 | 65 | 44 |
| 256×2304×768 | 75 | 87 |

而且每个形状的最佳参数都不同，没有一组参数能全面不输。原因分析：

1. **重复打包本来就不贵**：kNC=512 时 14 份 B 块一共 7 MB，L3 装得下；
   多出来的打包量只占每个线程计算量的 1/（分到的行数）。
2. **barrier 很贵**：每轮都要等最慢的核（LP-E 核）做完最后一个任务。
   K=3072 时一次矩阵乘要同步 24 次。
3. **M 小时工作单元不够分**：M=16 时只有约 12 个单元，14 个线程有的领不到活。

**教训**：先估算「被消除的开销」到底有多大，再决定要不要引入同步。
「看起来浪费」不等于「真的是瓶颈」。

### 6.4 多线程为什么离峰值还远

- 14 个线程里只有 4 个跑在 P 核上（2 核 × 超线程），E 核单核吞吐低得多，LP-E 更慢；
- 按行**平均**切分，P 核做完要干等 E 核（静态划分对混合架构不友好）；
- 15 W 功耗墙：全核满载时频率大幅下降。

## 7. 性能测量方法论

这一轮优化里，**测不准**造成的误判比代码 bug 还多。总结出来的做法：

**(1) 必须 Release。** Debug（`-O0` + ASan/UBSan）下 v2 只比 v1 快 1.1 倍，
Release 下快 30 倍 —— 两者的结论完全相反。

**(2) 预热 + 多次取最小值。** 干扰（调度、其他进程、cache 被挤）只会让某次变慢，不会变快，
最小值最接近真实速度。`hello_perf` 里每个版本预热 1 次，跑 5 ~ 9 轮取最快。

**(3) 只信同一进程内的交替对比。** 这台机器前后两次运行能差 30%，
持续满载降频时能差 3 倍。比较两个版本时：

```bash
# 把旧版本编进另一个命名空间，和新版本链接进同一个程序，交替运行
git show HEAD:src/kernel_matmul.cpp > old.cpp
g++ -std=c++20 -O3 -march=native -Dinference=oldinf -Iinclude -c old.cpp -o old.o
# 基准程序里声明 oldinf::kernel::matmul_f32_avx2(...)，和 inference::kernel:: 版本轮流跑
```

`-Dinference=xxx` 把命名空间整体改名，同一份源码就能编出多个参数版本
（配合 `sed` 改 `constexpr` 常量来扫参数），不用改任何代码。

**(4) 不要只测 2 的幂。** N=1024 会触发 4 KB 别名，N=1000 不会。
`hello_perf` 两种都跑，对照着看。

**(5) 不要只测方阵。** 推理里的矩阵乘 M 是 token 数，常常很小
（16×3072×768 这类形状），表现和方阵完全不同。

**(6) 每个优化版都必须和参考实现对拍。** `hello_perf` 里每个版本都和 v1 比对 `max_abs_diff`，
测试里和 double 精度的参考实现比对，容差随 K 线性放宽（`1e-6 × (K + 8)`）。

## 9. 思考框架：每一步是怎么想到的

回头看，每一版都遵循同一个循环：

```
   ┌──────────────────────────────────────────────────────────┐
   │ 1. 算上限：这一步理论上最快能多快？（FLOP、字节、峰值）       │
   │ 2. 找瓶颈：最内层循环每次迭代读了几次、写了几次、从哪一级读？  │
   │ 3. 提假设：换顺序 / 分块 / 打包 / 寄存器分块 / 并行           │
   │ 4. 做实验：同进程交替对比，换尺寸（2 的幂与否）、换形状        │
   │ 5. 对拍：结果必须和参考实现一致                              │
   │ 6. 解释数据：符合预期吗？不符合就回到第 2 步                   │
   └──────────────────────────────────────────────────────────┘
```

具体到每一版：

| 版本 | 看到的现象 | 问自己的问题 | 得到的答案 |
|------|-----------|-------------|-----------|
| v1→v2 | 0.5 GFLOPS | 最内层在读谁？是连续的吗？ | B 按列跳着读 → 换循环顺序 |
| v2→v3 | 能向量化了，但只有 17 | 数据被复用了几次？在哪一级 cache？ | B 每行 A 都从 L3 重流一遍 → 分块 |
| v3 第一版 | 分块了反而更慢 | 块真的留在 L1 里了吗？换个 N 呢？ | 4 KB 别名 → 打包 |
| v3→v4 | 卡在 20~30 | 每次 FMA 伴随几次 load/store？ | C 来回读写 L1 → 寄存器分块 |
| v4 第一版 | N=2048 只有 6.5 | 微内核读 B 的地址是什么样的？ | 跳着读 8 KB → 打包 B |
| v4 加 A 打包 | 没变快 | A 原来在哪一级？占多大？ | 4 KB 本来就在 L1 → 不是瓶颈 |
| v5 共享 B | 反而变慢 | 被消除的开销有多大？引入的开销有多大？ | 打包开销很小，barrier 开销更大 |

几个反复出现的规律：

1. **现代 CPU 算力过剩，瓶颈几乎总是「数据没及时送到」。** 每一步优化都是在提高数据复用率。
2. **连续访存是一切的前提。** SIMD、硬件预取、cache line 利用率都依赖它。打包就是「花一次拷贝，换来之后所有访问都连续」。
3. **2 的幂是陷阱。** 行距是 4 KB 的整数倍时，cache 组冲突会让分块失效。
4. **假设要用数据验证。** 「A 打包应该更快」「共享 B 应该更快」都被实验否定了。

## 10. 未来可以做的优化

按「对本项目推理性能的价值」大致排序。

### 10.1 优化 NT 版本（`matmul_nt_f32`）—— 推理真正走的路径 ⭐

`ops::linear`（`src/ops.cpp`）调用的是 `matmul_nt_f32`（`C = A × Wᵀ`，W 是 `[N, K]`），
**不是**本文的 v1 ~ v5。目前 NT 的 AVX2 版是 4×2 的点积分块 + 水平求和，没有打包、没有 GotoBLAS 结构。

做法：把 W 打包成和 v4 一样的 16 列竖条（打包时顺便完成转置），然后直接复用 v4 的微内核。
对推理来说这是收益最大的一步。

### 10.2 权重预打包（pre-packing）⭐

推理时权重是常量，每次前向都重新打包是纯浪费。
在模型加载时把每个 linear 层的权重一次性打包成竖条布局存起来，前向时微内核直接读。
M 很小（单 token 解码 M=1）时，打包开销占比最高，这一步收益最大。

### 10.3 小 M 专用路径（GEMV）⭐

自回归解码时 M=1，矩阵乘退化成矩阵-向量乘（GEMV），是纯**内存带宽受限**的：
每个权重只用一次，没有复用可言，GotoBLAS 那套分块没用。
优化方向：按列（N）切给多线程、流式读取权重、减少权重字节数（见 10.6 量化）。

### 10.4 按列切分的多线程

M < N 时（推理的常态），按行切每个线程只分到几行，而且每个线程都要打包整份 B。
改成每个线程负责 C 的一段列，只打包自己那一段 B —— 不重复打包、也不需要 barrier。
需要先让 v4 支持任意行距（`lda / ldb / ldc` 参数）。

### 10.5 6×16 微内核

累加器从 8 个增加到 12 个（6 行 × 2 个 `__m256`），加上 2 个 B、1 个 A 广播共 15 个寄存器。
FMA 延迟 4 周期 × 2 个端口 = 需要至少 8 个独立累加器才能填满流水线，8 个是临界值，12 个更从容。
BLIS 在 AVX2 上用的就是 6×16。预计单线程再提升 10% ~ 20%。
注意 kMC 要改成 6 的倍数。

### 10.6 量化：INT8 / FP16 / BF16

- 本机支持 **AVX-VNNI**（`vpdpbusd`）：一条指令做 32 个 int8 乘加，理论吞吐是 fp32 FMA 的 4 倍；
- 权重字节数减到 1/4，对 10.3 的带宽受限场景直接提速 ~4 倍；
- 需要配套：量化 / 反量化、per-channel scale、精度对拍。

### 10.7 算子融合（epilogue fusion）

linear 之后通常紧跟 `+ bias` 和 `gelu`。现在是三个独立的 pass，C 要读写三遍内存。
在微内核写回 C 之前（寄存器里）直接加 bias、做激活，只写一次。

### 10.8 持久线程池

每次矩阵乘都创建、销毁 14 个 `std::jthread`（每个几十微秒）。
推理时一次前向有几十上百次矩阵乘，小矩阵上线程开销占比很大。
改成启动时创建一个线程池，矩阵乘只投递任务。

### 10.9 混合架构感知的调度

- 动态分配任务而不是平均切分，让 P 核多干（6.3 的实验说明：任务粒度要够细，且不能频繁全局同步）；
- 或者只用 P 核（`set_num_threads(4)` + 绑核），对比一下是不是反而更快。

### 10.10 其他

| 方向 | 说明 |
|------|------|
| K 循环展开 + 软件预取 | 微内核里手动展开 2~4 次、`_mm_prefetch` 下一条竖条；收益通常 5% 左右 |
| 对齐分配 | 打包缓冲区 64 字节对齐，用 `_mm256_load_ps` 代替 `loadu` |
| 大页（huge pages） | 减少 TLB miss，大矩阵上有效 |
| 自动调参 | 启动时针对本机扫一遍 kMC/kKC/kNC，存起来 |
| AVX-512 / AMX | 本机（135U）不支持；换到服务器 CPU 时是下一个台阶 |
| Strassen 等快速算法 | 渐近复杂度更低，但常数大、数值稳定性差，推理引擎基本不用 |

### 10.11 对标

接下来最有说服力的一步：在同一台机器上跑 OpenBLAS / oneDNN / Eigen 的 sgemm，
看看自己的 v5 达到了它们的多少 —— 知道差距才知道该往哪里使劲。
